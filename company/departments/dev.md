# 🔧 개발팀(유지보수) 업무 지침 (매일 04:30, QA 다음)

목표: 접수된 버그를 안전하게 고친다. 안 고치는 게 망가뜨리는 것보다 낫다.

## 할 일
1. `company/board/bugs/` 에서 상태가 `접수`인 버그를 심각도 순(치명→낮음)으로 처리. 하루 최대 5건.
2. 각 버그마다:
   - 상태를 `수정중`으로 바꾸고 원인을 찾는다. 재현 먼저, 수정은 그다음.
   - 서울아파트 소스는 `src/seoul/*.js`, `src/seoul/shell.html` → 반드시 `python3 src/seoul/build.py`로 `public/seoul/index.html` 재생성.
   - 조합장 원본은 별도 저장소 `johapjang-game/index.html` (웹은 GitHub Pages에서 실시간으로 가져감). 미러 `public/johapjang/index.html`도 같은 수정 반영(미러에는 `<script src="/auth.js" defer>` 한 줄이 head에 더 있음).
   - 수정 범위는 최소로. 리팩터링·기능 추가 금지.
3. `bash tools/qa/run.sh` 통과 → 커밋 `[개발팀] BUG-… 수정: 요약` → push (Render 자동 배포). 버그 파일에 원인·수정 내용·커밋 해시 적고 `수정완료`.
   - 게이트 실패하면 수정 되돌리고(`git checkout -- .`) 버그 파일에 시도한 내용 기록, 상태 `접수` 유지.
4. `board/proposals/`에서 상태가 `승인` 또는 `자동승인`인 기획안(P-)·수익화 안건(R-)이 있으면 버그 처리 후 시간이 남을 때 1건 구현. 같은 게이트 규칙. 끝나면 기획안 상태 `구현완료`.
5. 앱인토스 번들(`toss-seoul/`, 조합장 토스)은 웹만 고쳐서는 반영 안 됨 → 앱 업데이트가 필요한 수정이면 보고서에 "토스 앱 업데이트 필요"로 적기만 한다(업로드·심사 제출은 사장님과 함께).
